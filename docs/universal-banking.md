# Universal banking implementation evidence

Implementation evidence checked 26 October 2026; backend deployed at `6e8376d6`. Frontend release verification is tracked in `tasks/banking/release.md`. This document distinguishes software tests from bank authorization. No bank sandbox credentials or live merchant accounts have been supplied; no official sandbox/live transaction test or certification is claimed.

## Shared implementation

`BankProviderAdapter` separates bank protocol and account-bound evidence from accounting. `BankProviderRegistry` discovers configuration fields and implemented capabilities. The composition list is `registered-bank-providers.ts`. Safaricom retains its existing adapter and shares the verified inbox, allocation and ledger services.

Equity Jenga implements merchant authentication, registered RSA-SHA256 request signing, account-bound full-statement retrieval and diagnostic transaction lookup. The transaction lookup omits receiving-account evidence and cannot authorize allocation. The adapter uses the documented sandbox/live hosts, rejects redirects, bounds requests/responses and does not persist provider error bodies or credentials.

KCB Buni account IPN verifies the RSA-SHA256 signature over the delivered JSON, binds the signed receiving account to the approved school revision and normalizes exact KES credits into the same inbox. KCB must supply the signing public key through independently verified platform onboarding; school staff cannot replace that trust anchor. Connection checks and activation require a recent, non-conflicting bank-signed notification for the current credential version. A key change during receipt rejects the delivery for retry. Notifications received before activation remain visible for reconciliation and do not post automatically.

Co-op Connect implements the public 1.0.0 sandbox account-validation and full-statement endpoints using an authorized bearer token. It validates the echoed request ID and receiving account and separates credit/debit postings by their stable posting ID. Its adapter, server configuration and activation guards allow sandbox only. The public response omits currency, the account-length schema contradicts its example, and the public transport does not establish production/token-renewal contracts. Sandbox setup therefore requires a bank-confirmed 14-digit KES account and a token obtained through the authorized portal. Live statements remain available.

The existing payments worker dispatches retrieval through BullMQ, below callback priority. PostgreSQL keeps per-school/account checkpoints, expiring leases and retry backoff. Retrieval persists a complete date before advancing it and revisits the preceding two days for delayed posting. A saturated/incomplete response leaves the date pending with a visible error. Staff can request an audited retry/backfill after account activation; older evidence uses reviewed statements. Credential replacement for the same account inherits its pending cursor.

Incoming credits enter the existing payment inbox and shared financial posting. Debits remain review items for reconciliation and approved reversal; they are never converted into incoming payments. Sandbox evidence tests matching without creating live fees, receipts or ledger entries. Native identifiers, original bank references and statement serials remain traceable. Manual bank receipts and imported statements share reference locks with native collections, preventing cross-path duplicate receipts.

Accountants submit the account for Principal approval, enter supported bank credentials through dynamic fields and run an account connection check. Credentials remain encrypted and absent from read responses. Super Admin controls activation and suspension. Configuration, retrieval health, error/retry controls, events, notifications and audit records use the established Payment Setup workspace.

## Verification boundaries

Real PostgreSQL tests cover forced school RLS, inbox identities, concurrent processing, manual/statement/native duplicate prevention, retries, incomplete dates, expired leases, sandbox isolation and same-account credential replacement. A test-only twelfth provider registers through the public adapter contract and uses the unchanged retrieval/inbox flow; removing it preserves financial history and other providers. The HTTP ingress tests stub the final receipt poster. The additional `bank-accounting-chain.integration-spec.ts` suite uses real Prisma, schema bootstraps, inbox, receipt, credit, allocation, suspense and ledger services, with local normalized provider fixtures and transactional event/notification test sinks. It verifies ledger conservation, duplicate execution, rollback/recovery, school isolation and approved reversals. Neither suite is official bank certification.

KCB's published OpenAPI timestamp example has minute precision; the account PDF example has an inconsistent 13-digit value. The adapter accepts strict 12/14-digit East Africa timestamps and rejects ambiguous dates. Bank onboarding must confirm the actual delivery format. Missing KCB notifications use reviewed statements until a bank retrieval contract is available. No unsupported polling, Daraja simulator or validation endpoint is presented for KCB.

JSON monetary numbers retain their source decimal tokens before conversion to integer minor units; string amounts use the same exact decimal validation. This prevents hidden fractional cents or floating-point rounding from changing a payment.

## Historical invoice adoption

Accountants can inspect **Invoices & statements → Historical invoices**. Principals can review and adopt selected records from **Fees → Historical invoices**, with a required review reason. The server requires Principal/owner permission, school ownership and the current source fingerprint. Invalid balances, missing learners, duplicate numbers and conflicting canonical invoices remain exceptions. Selection is limited to 100 records per transaction; the screen pages 50 records at a time.

Adoption preserves the original invoice ID, number, learner, academic labels, total, paid amount and source row. It records immutable lineage and a source snapshot, audit and event in the same transaction. Paid amounts appear as historical opening adjustments; adoption creates no receipt, cash posting or fabricated payment date. Where legacy records have no due date, their original creation date is the explicit due-date fallback. Existing canonical records require matching source lineage and amounts; matching an invoice number alone cannot authorize adoption.

The old `/finance/invoices/generate` URL now uses the canonical billing roster, duplicate guard and credit application. Its configured fee structure determines the academic period; mismatched overrides are rejected. `/finance/fee-structures` shares the validated billing DTO and audited service. Finance reads combine canonical and remaining legacy invoices. Unadopted historical charges prevent billing the same learners for that fee structure again.

Deployment adds the lineage table and source-protection trigger; it does not automatically migrate any school. The operator-only schema down script is tested before adoption and refuses to run once lineage exists. After adoption, keep the canonical billing path and lineage when rolling back application changes; use audited forward corrections for financial history. No destructive backfill or source-table removal is included.

## Reconciliation corrections and financial integrity

Collections now exposes **M-Pesa reconciliation reviews** for Accountants and Principals. A correction requires a reason, explicit confirmation, two reviewers distinct from its requester, and final Principal approval. For a collection-backed receipt, final approval executes the existing governed reversal, restores original and later credit allocations, verifies the resulting ledger record, and resolves the discrepancy in the same database transaction. Failed financial execution or audit/event persistence leaves the request pending and the discrepancy unresolved. Pending requests can be cancelled by their requester or Principal with an audited reason. An accounting reversal does not initiate an external refund.

Matched and reversed legacy C2B receipts retain their terminal state when delayed verification arrives. Collection reversals update the linked C2B status, with consistent row lock order. Historical reversal approvals without execution proof can be reopened with a reason: a new request requires two fresh independent reviews, while the original decision and resolution evidence remain preserved. Reopening never inherits old reviewers or changes balances. Non-reversal corrections execute through the governed workflows described below; approval without financial execution proof cannot resolve a discrepancy.

Historical completed STK receipts use the same reconciliation review flow. Staff can choose **Request reversal** in the receipt register, including when no automatic discrepancy exists. The server creates an explicitly staff-requested review using the stored amount and provider reference; retries return the same pending request. Execution verifies the same-school provider receipt, original ledger, learner, approved amount and allocation/credit conservation before reversing the original ledger entries. A separate immutable, school-scoped reversal record preserves the original successful intent and allocation history. Applied credits are reversed and unused credit is removed atomically; concurrent credit application and repeated execution serialize. Incomplete historical allocation evidence remains an explicit reconciliation exception. Accountant statements and linked Parent/Student histories use the shared receipt projection, including reversal status. This corrects a former portal gap that omitted older STK receipts entirely.

The full-chain tests reproduced and fixed clean-start UUID/text receipt-to-ledger foreign-key incompatibility, an allocation conflict clause that did not match its partial index, Prisma-incompatible advisory-lock results, and a billing lock that was never acquired. Receipt reversals now reject insufficient recorded invoice balances and retain void/uncollectible status instead of silently clamping a balance or reopening an exited invoice. UUID and text ledger schemas both retain enforced foreign keys across bootstrap retries.

Daily C2B review excludes an already corrected receipt only when its same-school collection, original ledger, reversed receipt and reversal ledger agree on amount and currency. Unproven provider reversals and mismatched evidence remain exceptions. Real Prisma testing also reproduced and fixed a fee-waiver advisory-lock result that prevented requests; concurrent retries now create one waiver and preserve cash postings. The accounting/waiver/governance regression passed 31 PostgreSQL checks.

STK correction events notify only the learner's active, same-school guardian and student portal accounts. Reconciliation recognizes linked collection, suspense and reversal ledger records through durable amount/currency-matched provenance; unexplained entries remain visible. Focused real-PostgreSQL verification passed 19 checks. Eight production-build browser journeys passed at 390px and 1440px across Accountant, Bursar, Principal and Super Admin, using explicit local API fixtures rather than a live school or bank.

Full-receipt refund evidence can be recorded from an already reversed receipt in Payments and reviewed in Collections by a different Principal. The server requires the exact reversed amount and matching original/reversal ledger records, an outgoing reference, actual paid date, evidence location and reason. Duplicate references/reversals are serialized; completed evidence is immutable and rejected evidence remains in history. This records an externally executed payout, not a bank-verified transfer instruction. The original reversal remains the only financial posting.

Unused credit has a separate **Credit refunds** workflow. From Invoices → Learner balances, staff select the original receipt and a precise partial amount. A request reserves that credit, a different Principal approves or rejects it, and authorized finance staff record an actual payout through the original payment channel with an outgoing reference and evidence. This does not initiate a bank/M-Pesa transfer. Pending and approved amounts remain owned by the student but are unavailable to automatic/manual invoice allocation. Cancellation or rejection releases an unpaid reservation; recording the payout posts one balanced refund through the existing ledger and removes only that amount of credit. Statements preserve the original receipt and show a dated refund debit; linked Parent/Student portals show refund amounts, dates and references. Daily collections remain gross receipts; refunds are separately traceable in their queue and ledger.

Requests, decisions, payout evidence and ledger links retain immutable history with forced tenant RLS and audit/events. Source locks and the existing student credit lock serialize invoice allocation, refunds and receipt reversals. Duplicate submission/payout retries do not post again; references cannot be reused across credit refunds and full-receipt refund evidence. A full reversal is blocked while a refund is reserved or after it has been paid, preventing double withdrawal. Unpaid reservations can be cancelled; correcting a receipt with an already paid refund requires reconciliation. Invalid allocation ownership/conservation or an unsupported historical multi-account ledger requires reconciliation rather than guessed postings. Original two-entry receipt ledgers are supported; this workflow returns through their original clearing/control accounts. Reconciliation recognizes completed refund ledger proof only when amount and currency agree.

## Governed non-reversal corrections

The workspace is now named **Financial correction reviews**. Accountants can request moving a posted collection, manual receipt or historical STK receipt to the correct same-school learner, matching a verified unmatched collection, or writing off a selected unpaid invoice amount. Every request has a durable retry key, server-derived original-receipt snapshot, reason and explicit confirmation. Two independent reviewers, including a final Principal, must approve; the requester cannot approve their own request. Client-supplied evidence cannot override authoritative receipt, learner or invoice identity.

Moving a receipt reverses the original allocation and posts a replacement against the same clearing/control accounts, with equal amount, currency and correction effective date. It preserves the original receipt and attaches immutable correction lineage. It cannot create cash or reuse a reversal that already funded an external refund. Reviewed matching uses the same verified collection engine and synchronizes C2B placement. An invoice write-off reduces only its unpaid amount; it does not create a payment or close an unexplained bank discrepancy. Failed execution, stale snapshots, pending refunds and inconsistent allocations remain explicit exceptions. Concurrent execution and retries return the existing result.
