# Report-card engineering report and operations guide

Repository implementation: September 2026. Changes are local and validated with disposable infrastructure; they have **not been deployed to Railway, Vercel or Cloudflare**. This is a horizontally scalable implementation, not a certification of 10,000,000 reports/day. The remaining capacity and delivery guarantees are stated explicitly below.

## Engineering report

1. **Initial architecture.** Next.js called Nest endpoints that loaded academic data, assembled snapshots and rendered PDFKit documents. Generation rendered both HTML and PDF but persisted artifact manifests rather than PDF bytes. Individual downloads rendered again. Small bulk exports rendered during HTTP requests; larger exports used BullMQ, temporary PDF files and PostgreSQL byte chunks. Worker consumers ran inside ordinary API processes. Redis retained export status for less time than exported files. Existing snapshot versions, review rules, advisory locks, scope confirmation and the PDFKit streaming renderer were useful and have been retained.

2. **Main problems.** Repeated rendering; CPU sharing with HTTP traffic; approximately 20 SQL operations per newly generated report in the measured workflow; redundant HTML work; bulk data in PostgreSQL and browser memory; browser-driven batch orchestration; transient queue status; inadequate source-change invalidation; remote objects surviving metadata cleanup; stale permission checks; and upload failure/temporary-file races. One guardian download path rendered snapshot JSON instead of the official report layout.

3. **Chosen architecture.** The authenticated API validates and persists requests. PostgreSQL owns job state. Two separate Railway worker lanes execute interactive preparation and bulk generation/export. BullMQ transports bounded batches of job IDs. Existing PDFKit/domain services render snapshots. The existing object-storage interface writes private R2 objects. The browser receives a short-lived, object-specific download URL after fresh authorization and freshness checks.

4. **Why stronger.** Report CPU and temporary files move off API replicas; job state survives Redis loss; SQL uniqueness and leases arbitrate concurrency; immutable snapshots and stored PDFs eliminate repeated individual rendering; bulk uploads/downloads avoid whole-file buffers; failures remain visible and recoverable. No new cloud rendering service, Cloudflare Worker or AWS dependency is introduced.

5. **Vercel.** Hosts the Next.js UI, existing authenticated API proxy, preview controls and job polling. It does not render PDFs, run queues or store report files. Primary staff downloads navigate directly to R2 without loading the PDF into JavaScript memory.

6. **Railway.** The existing Nest API performs authorization, scope confirmation, durable enqueue, status and delivery authorization. Independent `reports-worker` services render/upload and perform retention cleanup. Keep interactive and bulk workers separate; the worker module loads report dependencies without the full HTTP application or unrelated event consumers.

7. **PostgreSQL.** Stores academic source data, immutable report snapshots, review/publishing history, artifact manifests/checksums, source revision counters, durable work/progress/leases, upload reservations, audit and event outbox. New report bytes live in R2 in production. The small database-storage fallback remains for development and existing files.

8. **Redis/BullMQ.** Provides work delivery, worker locks and stalled-job handling, not the durable record of a request. Dispatchers feed at most 32 IDs per pass and aim to keep each waiting/delayed lane below 64; simultaneous dispatchers can briefly overshoot that threshold. PostgreSQL reservations and dispatch versions recover lost Redis jobs. A dedicated report Redis is supported through `REPORT_REDIS_URL`.

9. **Cloudflare R2.** Stores permanent report PDFs and expiring combined export PDFs in a private bucket. The existing S3-compatible SigV4 adapter routes report academic/temporary paths to dedicated REPORT_OBJECT_STORAGE_* R2 credentials, preserving existing UPLOAD_OBJECT_STORAGE_* providers for legacy school uploads. Production validation requires R2 for report artifacts. R2 serves the large bytes directly; no public bucket or permanent public URL is needed.

10. **Individual generation/download.** Ordinary generation first checks the current snapshot and stored artifact; a valid hit returns immediately. A miss becomes durable interactive work. Generation loads and validates inputs, renders one PDF, stages its bytes, then persists the snapshot/manifest and promotes storage atomically with academic audit/outbox state. Preparing an existing card either returns its authorized delivery URL or queues missing-PDF work. Guardian/student access retains relationship and published-state checks and reads the official saved PDF through its existing authenticated download path.

11. **Large exports.** Every bulk export is asynchronous, including small selections. Server-confirmed class, stream, form/grade or school scopes are limited to 20,000 reports per export. Workers read snapshots in batches of 50, reuse a bounded image cache, spool one PDF with backpressure and stream one upload. Limits: 20,000 pages, 512 MiB and 15 minutes of rendering. Larger scopes must be split. Class generation runs in checkpointed chunks of 25 with four student tasks per chunk; it releases the tenant lane between chunks. The UI shows progress, recent tasks, partial failure and retry, and does not need to remain open for work to finish.

12. **Reuse.** Canonical SHA-256 identities include tenant, snapshot/card identity, verification code, meaningful payload and renderer version. Generation also binds source revision. An individual valid artifact needs no renderer. Concurrent identical requests share a job; concurrent PDF uploads elect one cache winner. Completed matching exports can be reused by another authorized actor in the same school, while each actor's job remains private and receives its own export audit. Reuse never extends the original export expiry.

13. **Invalidation/regeneration.** Transactional database triggers increment school or student source revisions for marks, grading, attendance, comments, enrollment, cohort results, templates/settings, branding and signers. Changes to referenced stored image bytes invalidate reports too. Scheduled grading-policy boundaries impose an additional validity deadline. Shared signer-account changes invalidate all dependent schools through a restricted trigger with a pinned schema lookup path. Freshness is checked before work, after rendering and before delivery. Source changes require controlled regeneration and review; existing approvals are not silently transferred to changed academic content. Visibility-only publication does not re-render identical bytes. Bump `REPORT_RENDERER_VERSION` when changing layout/fonts or interpretation.

14. **Retries/idempotency.** Tenant advisory locks serialize admission; at most 20 queued/running tasks are admitted per school. One task per school per lane executes at a time, across replicas. UUID leases, dispatch versions, a 90-second lease and 15-second heartbeat fence old workers. Transient jobs retry up to three attempts with backoff; validation/authorization conflicts fail without retry storms. Chunk checkpoints preserve saved work. Explicit partial-failure retry starts the scope again and reuses successful cards. Missing-artifact repair can requeue a completed preparation job. Every upload attempt uses a random object key; unpromoted attempts expire.

15. **Retention.** Permanent academic PDFs, snapshots and audit history have no temporary expiry. Temporary combined PDFs and upload reservations expire after 24 hours. Superseded, unpublished draft PDF bytes receive 30-day retention. Historical published records remain permanent. A bulk worker sweeps bounded batches every 10 seconds, deletes remote bytes before metadata and retries failures. Expired work rows are retained for a further day before removal; academic audit/outbox records remain separate. Known abandoned local report spools older than 24 hours are removed on bulk-worker startup without recursive deletion or symlink traversal. Do not put an age-based R2 lifecycle rule on the shared academic prefix.

16. **Isolation and private delivery.** Trusted request context determines tenant and actor; identifiers from the browser never select tenancy. New tables enforce RLS, tenant-aware unique keys and explicit SQL tenant predicates. Job access additionally requires its original actor. Workers reconstruct scoped execution and recheck active membership, role, capability and module access. Paths include tenant plus random identifiers, with no student names. Storage rejects foreign prefixes and traversal. SigV4 binds the exact object, parameters, response headers and expiry. Fresh URL issuance rejects changed, withdrawn, expired or unauthorized reports. **An already issued R2 URL is a bearer capability valid for up to 60 seconds; logout, revocation or source changes cannot instantly revoke that URL, and an already started download can continue.** Absolute per-byte revocation is not provided by this direct-delivery design. See [Cloudflare's presigned URL model](https://developers.cloudflare.com/r2/api/s3/presigned-urls/). Previously downloaded files also cannot be recalled.

17. **Protection for normal traffic.** No bulk rendering or queue consumption in the API; independent worker CPU/memory and lane replicas; bounded generation/export work; per-school quotas and lane gates; limited database pools; bounded Redis delivery; and direct R2 transfer. Database and Redis are still shared dependencies unless report Redis is separated. Increasing worker replicas without respecting database capacity can still degrade ordinary traffic.

18. **Repository changes.** Added report artifact/work/retention services, source revision schema/triggers, the standalone Railway worker/module, worker deployment/environment examples and the benchmark harness. Updated generation, snapshots/manifests, scope eligibility, private storage/delivery, controller contracts, guardian download, production validation, pool sizing and tenant policy registry. Updated the main report workspace, two older workspaces, shared API client and frontend action tests. Added backend unit and real PostgreSQL/Redis integration coverage. The bootstrap follows the repository's existing additive schema mechanism; there is no unrelated Prisma migration or new infrastructure SDK.

19. **Validation.** See the reproducible commands and measured results below. Tests cover generation, reuse, source changes, protected published snapshots, duplicate delivery, tenant/actor boundaries, permission revocation, lease recovery, partial retry, Redis queue loss, stored PDF bytes, atomic audit/outbox rollback, upload/delete failures, private signatures, image failures, limits and spool cleanup. Local renderer measurements establish bounded memory and process separation. They do not measure production Railway, full Nest API latency or live R2 throughput.

20. **Production configuration.** The API, interactive/bulk workers, private R2 and matching Vercel UI were deployed on 24 September 2026. See [the deployment record](report-card-deployment-2026-09-24.md) for exact settings, checks, backup limitations and rollout incidents. Alert routing, long-term backup policy and authenticated school acceptance remain operational work.

21. **100,000+ reports/month.** No architectural blocker was found at this volume, but report correctness depends on migrated snapshots and valid uploaded logos/signatures; production availability requires both worker lanes, adequate database capacity and operational monitoring. Limits apply per export, not per school/month. Shared-school changes conservatively invalidate more reports than strictly necessary. Production memory for unusually large images, peak-period throughput and the 60-second issued-link window remain explicit operational considerations.

22. **Beyond that volume.** The next likely limit is source-query/database write throughput, then event/audit growth and rendering of image-heavy reports. Ten million *new* cards/day is about 116 cards/second averaged over 24 hours, with substantially higher peak demand. At the measured roughly 20 SQL operations/card, budget thousands of database operations/second before approval, download and polling traffic. Horizontal report replicas do not remove this database cost. Multi-year operation at that rate requires measured pool sizing, query batching/read models, retention-aware partitioning/archival for operational history and database capacity planning. The worker/artifact pipeline can scale without changing its public contract, but **10M/day comfort and headroom have not been established by these tests**.

## Rollout and compatibility

1. Back up PostgreSQL and review the changed production validation before deploying. Create a **private** R2 bucket with bucket-scoped read/write/delete credentials. Disable public access, public custom domains and `r2.dev` access. Use the account's standard R2 HTTPS endpoint and region `auto`. Never overwrite immutable report/image object keys outside MyShule or delete objects behind its metadata. Restrict credentials to the backend and workers, never Vercel client variables.
2. Apply [the environment example](../deploy/railway/reports.env.example) to the existing API and both workers, preserving all existing production auth/tenant configuration. Set dedicated REPORT_OBJECT_STORAGE_* credentials; keep UPLOAD_OBJECT_STORAGE_* unchanged to preserve existing school uploads. Existing database-backed files remain readable; they are not copied or deleted as a side effect of this rollout.
3. Deploy the updated API first during a coordinated release window. Existing schema bootstrap creates the four report tables, indexes, RLS and triggers after domain tables exist. The operational database login must own/manage schema and have the existing BYPASSRLS capability; request transactions must assume the existing `NOBYPASSRLS` runtime role. Never use the operational login directly for request-owned queries. The signer's restricted trigger is the only added cross-school identity invalidation operation and returns no school data.
4. Create **two Railway services** using the settings in [reports-worker.railway.json](../deploy/railway/reports-worker.railway.json), with `REPORT_WORKER_LANE=interactive` and `bulk`. Current Railway rejects the legacy JSON configuration mechanism, so persist the start command, restart policy and shutdown timings directly in service settings (or migrate to its supported IaC). Start with `REPORT_WORKER_CONCURRENCY=1`, one replica each and measured memory headroom. No HTTP listener or HTTP health-check path is required. Alert separately on queue age because process uptime does not prove work is progressing. Scale lanes independently. The worker still needs the existing required production environment because it reuses domain configuration validation.
5. Both lanes must use the same `REPORT_REDIS_URL` (or existing `REDIS_URL`) and `QUEUE_PREFIX`. API submission does not call report Redis. Use private networking/TLS as appropriate, `noeviction`, persistence and bounded Redis memory alerts. Do not share the report queue with an incompatible old worker version. Existing event workers must remain deployed to dispatch saved audit/notification events.
6. Budget PostgreSQL connections across **both** Prisma and the existing `DatabaseService` pool per process, plus up to two schema bootstrap connections. Defaults are 20 connections per API pool and 5 per worker pool, not a single shared total. Existing DATABASE_MAX_CONNECTIONS remains the API fallback when DATABASE_API_MAX_CONNECTIONS is unset. Use actual replica counts when sizing PostgreSQL/PgBouncer. Keep ordinary API capacity reserved rather than increasing worker concurrency to compensate for a database backlog.
7. Deploy the updated Vercel UI with its existing API routing. No R2 secret, new rendering runtime or cron is needed on Vercel. PDF link navigation does not require CORS fetch access. Retain the existing API proxy/cookie configuration.
8. Old snapshots without `source_revision` are validated by staff's Prepare/Download action or existing class generation workflow. Class generation certifies matching legacy snapshots in its bounded worker chunks, so staff need not open each student individually. If rebuilding the current payload is identical, the worker preserves publication/verification and materializes its PDF. If inputs differ, controlled regeneration and normal review are required. Do not backfill revisions blindly. Bulk and guardian freshness checks intentionally withhold uncertified legacy snapshots until this verification completes. Schedule a staff migration pass for historical published reports before opening the reporting period.
9. Generation endpoints now return either a valid existing result or a durable job. The old bulk-PDF GET is retained as a queued JSON entry point; external consumers expecting immediate binary data must adopt POST export plus status polling. All repository UI consumers have been updated. A browser poll timeout does not cancel saved work; reopen Recent report tasks.
10. On rollback, stop new worker consumers and restore a compatible API/UI pair together. Preserve snapshots, objects, work rows and source triggers; additive tables do not need destructive rollback. Old code would reintroduce the original delivery/invalidation behavior, so rollback is not a safe way to bypass a failed freshness check. Drain old deployments before enabling new workflows.

## Acceptance and measurement

Run from the repository root, using Node 22, installed dependencies, PostgreSQL binaries and `redis-server` available locally (or `TEST_REDIS_BINARY`). The database harness refuses production hosts and creates/disposes its own cluster. Do not substitute live database or Redis credentials.

```powershell
npm run test:report-infrastructure
npm --prefix apps/web run test:design -- --runTestsByPath tests/design/report-card-scopes.test.tsx tests/design/live-report-card-actions.test.tsx tests/design/report-card-generation-readiness.test.tsx tests/design/principal-report-card-release.test.tsx tests/design/dashboard-action-contract.test.ts
# From apps/web:
npx tsc --noEmit
# From repository root, after npm run build:
$env:REPORT_BENCHMARK_CARDS = '10000'
npm run benchmark:reports
```

Measured on this workstation:

| Exercise | Result | Boundary |
| --- | --- | --- |
| Two separate compiled renderers, 10,000 cards each, nine subjects | 55.75 / 56.06 seconds; 47.85 MB per PDF; peak RSS 181 / 191 MiB | Snapshot fixtures, no real images, database or R2; each file streamed and cleaned |
| Separate HTTP probe during those renderers | 1,800 samples; p95 2.85 ms; maximum 50.29 ms | Synthetic local HTTP server, not the Nest production API |
| 100 newly generated cards, seven subjects, PostgreSQL + real PDF + stored bytes + audit/outbox | About 4.42 seconds; 2,212 SQL operations; 761 KB total artifacts in the final publication regression run | Local test fixture and database storage; compiler-heavy Jest process RSS is not production worker memory |

The benchmark is a capacity diagnostic, not an SLA extrapolation. Validation passed 233 report backend unit tests, 33 PostgreSQL/Redis integration tests and 162 frontend tests across seven suites. The existing certification harness's 34 tests and the combined database/exams unit suite (167 tests, overlapping the report suite) also passed. Backend compilation and frontend TypeScript checking passed. Local detailed results are under `tmp/report-*.log` and `tmp/report-*-benchmark.json` and are not deployment inputs.

Before production acceptance, use a staging tenant and real private R2 to verify a first generation, repeated download, changed mark, changed image, scheduled grading boundary, approved/published regeneration rules, guardian relationship checks and a large combined export. Exercise simultaneous schools; kill a worker during rendering/upload; stop and restore report Redis; interrupt R2 access; verify retry/cleanup, checksum, no cross-school access and expired URL denial. Measure the **actual** API p95, worker RSS/CPU, database pool waits/IOPS, Redis queue age and upload latency under the expected peak mix. Scale until the measured target plus headroom is met. These live platform tests were not run here.

## Monitoring and repair

Alert on oldest queued age per lane, failed/expired tasks, repeated lease recovery, API/database latency, connection saturation, Redis eviction/reconnection, R2 failures and retention lag. Worker logs include `report_work.completed`, `report_work.partial_failure` and `report_retention.swept`; task results remain visible to their owner. Dispatch/storage errors preserve durable state. Completion and failure events contain task IDs and counts rather than report payloads. A process can be alive while Redis is unavailable, so use backlog alerts.

For authorized database operators only, aggregate health queries contain no report payloads:

```sql
SELECT kind,state,count(*),min(created_at) AS oldest,
       count(*) FILTER (WHERE lease_until < now()) AS expired_leases
FROM report_work WHERE expires_at > now() GROUP BY kind,state;

SELECT retention_policy,count(*),min(retention_expires_at) AS oldest_expired
FROM file_objects WHERE retention_expires_at <= now() GROUP BY retention_policy;

SELECT count(*),min(expires_at) AS oldest FROM report_object_uploads
WHERE expires_at <= now();
```

Do not log signed URLs, secrets or complete report payloads. The UI retry action rechecks current authorization; changed scopes need a fresh preview, changed academic data needs regeneration, and storage/Redis failures need dependency recovery. If an operator deletes an R2 object externally while keeping its database metadata, a signed URL cannot detect that missing object; reconcile that exact tenant/object metadata under a controlled repair before preparing it again. Automatic HEAD checks on every download were deliberately avoided. Periodic object inventory reconciliation and long-term academic retention/legal policy remain operational responsibilities.
